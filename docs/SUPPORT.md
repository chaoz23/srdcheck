# Support and maintenance policy

SRDCheck is alpha, community-maintained software with no SLA and no 24/7
on-call function. Supported Python and operating-system claims are limited to
`docs/support-matrix.md`; rules coverage is limited to runtime capabilities.

Use a GitHub issue for reproducible bugs, scoped feature requests, and public
documentation questions. Include version, adapter/data/rules identities,
query type, exit code, and a minimal synthetic request. Never include tokens,
private campaign/player data, commercial rulebook text, or confidential deal
information. For a sensitive vulnerability, use a private GitHub security
advisory if available; otherwise open a content-free issue asking the owner to
establish a private channel.

Response targets are best-effort planning goals, not promises:

- S1 acknowledgement: one business day when a maintainer is available;
- S2 acknowledgement: three business days;
- ordinary issues: triaged when maintainer capacity permits.

Maintainers may close requests that ask SRDCheck to overrule a DM, simulate the
game, ingest unlicensed content, conceal unchecked scope, or weaken citation
and refusal guarantees. Integrators own table consent, authoritative state,
Discord/VTT permissions, deployment availability, telemetry storage, and user
support for their host.

During an ownership transfer, the separately accepted agreement in
`docs/TAKEOVER.md` must provide at least 30 calendar days of named transition
support. That transaction-specific agreement supersedes these public planning
targets only for its named parties and dates.
